# SDRAM pipeline cache and clock bridge, 2026-10-19

The 72 MHz CPU / 54 MHz SDRAM image now runs the FP-RISC decision-tree
classifier (128/64 rows, 8 bins, depth 5) in **2,836,998 µs, against
6,608,712 µs for the 2026-10-18 image: 2.33 times faster**, on the board,
with the same binary and the same frozen CPU RTL. Two changes did it: a
64 KiB cache instead of 2 KiB, and a clock bridge whose writes stream through
an asynchronous FIFO instead of paying a clock-domain round trip each. A
third change, keeping a line valid when a store hits it, passes every
simulation but fails on the board, so it is off by default and recorded below
as open.

## Where the cycles went

A new simulation harness (`perf_tb.v`, `run_perf.py`) runs a preloaded image on
the generated CPU, the real cache, the real clock bridge, the real burst
controller and a functional SDRAM pin model under Verilator (about 0.6 million
CPU clocks per second), and counts what the cache holds the CPU for. It
reproduces the board: the unchanged design simulates the classifier in
6,516,759 µs against 6,608,712 µs measured (1.4%), and the final designs below
within 0.9%.

```sh
python3 boards/tangnano20k/sdram/run_perf.py \
  ../fprisc/build/tangnano20k-clock72/board/dtree-1/base.bin \
  --elf ../fprisc/build/tangnano20k-clock72/board/dtree-1/base.elf --line-bits 7
```

On the unchanged design, **71% of all CPU clocks were held** (335.7 of 470.1
million), almost all on read misses: the 125 KiB of code thrashes a 2 KiB
direct-mapped cache (6.98 of 9.53 million refills were instruction
fetches). Each refill cost 25.7 CPU clocks through the old mailbox bridge,
against 9.0 at a single 48 MHz clock, so splitting the clocks made every miss
about 1.9 times longer in wall time. That, not the CPU changes, is most of the
36% regression the [clock report](CLOCKS-2026-10-18.md) measured. Writes were
the next cost: every store is written through, each as its own round trip of
about 20 CPU clocks with one in flight, and every miss first waited for all
queued stores (14% of all clocks).

## Changes

- **Cache size** (`SDRAM_CACHE_LINE_BITS`, default 12 = 64 KiB, was 7 =
  2 KiB). The data array maps to 32 BSRAMs.
  64 KiB holds the classifier's whole program: code refills fall from 6.98
  million to 74 thousand.
- **Selective drain.** A refill used to wait for every queued store; it now
  waits only when a queued store is to its own line (four comparisons against
  the queue). Other stores complete after it.
- **Completion with the last beat.** The cache accepts `done` together with
  the final refill word, and the bridge sends it then, saving a clock per
  refill and per write.
- **FIFO clock bridge** (`clock_bridge.v`). Requests cross in a four-entry
  asynchronous FIFO: only Gray-coded pointers cross domains, through two-flop
  synchronizers, and a slot is never reused before the memory side completes
  it. The memory side executes in order, so a read never overtakes an earlier
  write; the cache's selective drain covers the stores it still holds. Writes
  are posted: the CPU side completes them when queued. Reads still collect all
  four words and replay them. The SDC false-paths only the first synchronizer
  stage of each pointer and of the read-response toggle; Gowin reports all
  three active, and payload slots keep normal setup/hold analysis.
- **Write-update** (`WRITE_UPDATE`, default 0). With 1, a store that hits
  writes its merged word into the cache and keeps the line, instead of
  invalidating it. See the open problem below.

In the final design 34% of clocks are still held: refills 31.6%, a full write
queue 0.8%, draining before a refill 0.6%. Most remaining refills (2.15
million) re-read lines that a store invalidated, which is what write-update
removes in simulation (2.05 against 2.81 seconds at 64 KiB).

The final image (`SDRAM_CACHE_LINE_BITS=12`, the default, placement option
2) meets internal timing at 72.145 MHz for the CPU (+0.028 ns, no setup or
hold violations) and 119.6 MHz for the memory clock. It uses 14,221 logic
cells (69%), 5,104 registers (33%), 37 of 46 BSRAMs and 3 DSPs. Timing closure
at 72 MHz is placement-sensitive: the 32 KiB invalidate build failed with
options 0 to 3 (worst paths inside the CPU, -0.44 to -1.70 ns) and passed with
option 4 (+0.005 ns).

## Verification

- `check_pipeline_cache.py`: seven cases. The fixture gained a store, another
  word, load-the-same-word pattern (the data BSRAM's same-edge collision) and
  a backend that sometimes completes with the last beat. Write-update keeps
  its own normal and X-poisoned collision cases; removing its whole-word
  forwarding, or the final-beat capture, fails as intended.
- `check_clock_bridge.py`: four clock-ratio/phase scenarios now include 240
  back-to-back posted writes that fill the FIFO, plus the real controller and
  pin model at 108/54 MHz with 0 and 6 ns access delay. Its pin-model rule
  "no completion on consecutive clocks" became "every completion matches
  exactly one accepted request".
- `check_pipeline_rtl.py --compressed --cdc-bridge` (generated CPU, cache,
  bridge, corrupt-beat rejection) and the actual boot ROM's T/Q/V/H upload
  through the real controller and pins at 54 MHz, 135 degrees, 5.4 ns: pass.
- On the board, both 32 and 64 KiB images: UART diagnostic, RV32C, the RAM
  and high-address checks, FP-RISC numeric, I32 and UART host services (host
  file contents checked), and the classifier against the independent Python
  reference. **The SD card cases were not run**: they write to the card's
  test partition and were not approved in this session.

## Open: write-update fails on the board

With write-update on, the classifier panics on the board right after
`DTREE BEGIN` (`apply: not a function value`, or `F64: invalid boxed value`).
The bisection so far:

- It fails at a single 54 MHz clock with no bridge in use (+2.5 ns slack), so
  it is neither the FIFO bridge nor 72 MHz timing.
- It fails with write-update alone (the original drain-everything rule), and
  also when a store that would hit the same word as the concurrent lookup
  falls back to invalidating, so it is not the same-address BSRAM collision.
- The original cache at the same 32 KiB size and 54 MHz passes (2,469,231 µs
  in 72 MHz units, 3.29 s real time).
- It passes every RTL simulation, including the whole classifier, and a Gowin
  netlist of the cache synthesized alone passes the cache fixture with
  Gowin's primitive models and 40 million clocks of the classifier under the
  CPU RTL with equivalent models.
- In the full netlist Gowin emulates the data BSRAM's read enable in fabric
  (the read port is always enabled, with a captured copy and a mux), which
  preserves RTL behaviour; the original cache has the same structure.

What remains is a gate-level simulation of the full in-context netlist (Icarus
manages a few hundred clocks per second; Verilator cannot compile Gowin's
primitive models, so it needs equivalent models for the DSP and PLL blocks
too), or on-chip observation.

## Also observed

One of eight classifier runs with the newly built FP-RISC binary printed a
negative elapsed time (`-104265506`) with correct results; the repeat was
correct. The CPU RTL and its CLINT are unchanged, so this looks like a torn
read of the 64-bit `mtime` in the runtime's timer, not the memory system.
