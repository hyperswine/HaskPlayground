# Pipelined RV32 over SDRAM (2026-10-16)

`SdramPipeline` connects the existing single-datapath RV32 pipeline to all 8 MiB
of SDRAM. It replaces the serial wrapper's wait on every word with a fixed
three-logical-clock cache port. `build.sh core` and `pipeline` select this image;
`serial` retains the earlier `SdramSimpleRisc` implementation.

## Memory path

- A unified, direct-mapped **2 KiB data array**, 128 lines of **16 bytes**, caches
  instructions and data. Each miss reads four consecutive 32-bit SDRAM words.
  Tags contain the full physical address; addresses separated by 64 KiB do not
  alias. ROM reads use the same logical latency without an SDRAM request.
- A **four-entry masked write FIFO** preserves store order and writes through
  to SDRAM. Stores invalidate their cache line; pending-store forwarding handles
  immediate reads. A line refill drains older writes first. There are no dirty
  lines or writeback evictions. Byte/halfword stores use actual byte enables
  rather than a CPU read/modify/write of the backing word.
- Misses, reset invalidation and a full write FIFO hold the CPU and all three
  logical memory stages together. Register-file writes also stop, preventing a
  pending write from repeating. Physical UART activity, refresh, `mcycle` and
  CLINT `mtime` continue; instruction retirement does not advance during a hold.
  Interrupt handling resumes when memory releases the CPU.
- The wrapper carries full byte addresses alongside the BRAM-sized legacy
  index. Its external word address is 22 bits: bit 21 selects ROM, and bits
  20..0 select all 2,097,152 SDRAM words. The map remains RAM at
  `0x80000000..0x807fffff`, ROM at `0..0x7ff`, plus the existing UART, finisher,
  CLINT and PLIC registers. The SPI/DMA I/O window remains unmapped.

The physical controller uses CAS2, sequential four-word reads and single-word
masked writes. Refresh runs independently, with priority before accepting an
operation. CPU and SDRAM use the same nominal frequency. Four-beat variants
use a 135-degree SDRAM output clock; the legacy single-word variants retain
225 degrees. No asynchronous clock-domain bridge was added.

The default ISA remains RV32IM plus the existing CSR/fence instructions.
`SDRAM_RVC=1` explicitly enables RV32IMC and mixed 16/32-bit fetch, including
instructions spanning a word or line. C-mode uses sequential prediction; the
word-indexed branch target buffer remains an IM feature. Smaller code therefore
does not automatically imply higher throughput.

## Evidence and current boundary

The generated Clash CPU, real cache and a delayed/backpressured backing-memory
model pass both IM and IMC execution. The guest checks high RAM addresses,
masked-store forwarding, instruction patching with `fence.i`, multiplication,
division corner cases, branches, precise traps, cycle/retirement/timer behavior
and UART Ctrl-C received during a 12,000-clock memory hold. C-mode also checks a
reserved 16-bit encoding's raw trap value and return at `pc+2`. Corrupting a
backend read beat must fail the executing guest and does.

The first pin model was wrong: it started driving the first read word one
SDRAM clock late. For a READ registered at edge N, CL2 starts driving after
N+1, with output-access delay, and is valid by N+2. This distinction is
explicit in [Micron's SDRAM data sheet, CAS Latency, printed page 14](https://people.eecs.berkeley.edu/~kubitron/courses/cs152-S04/handouts/256MSDRAM_G.pdf).
Earlier full-ROM and phase-sweep passes against the late model are superseded.

Both pin models now launch at `N+CAS-1`, with an optional output-access delay.
The old four-beat capture fails immediately: beat zero receives word one.
Capturing at `T_RCD+CAS` through `T_RCD+CAS+3` passes the corrected 27/48/54/66 MHz
controller tests, including 207 reads, 98 masked writes and 828 exact
beat comparisons, with a 6 ns injected delay and autonomous refresh. The
single-word legacy capture remains separate. C-mode actual-ROM UART upload
also passes at 27 MHz/225 degrees/6 ns with accelerated 32-clock UART bits,
and at 48 MHz/225 degrees/6 ns with the unchanged 868-clock UART timing,
checking cold RAM, every uploaded word, the sentinel, exact read beats and
guest output. The production controller passes the 27/48/54 MHz functional
pin suites; these passes do not establish a physical read window.

These are functional tests. The injected delay is a test input, not the
embedded SDRAM's characterized limit. They exclude FPGA I/O routing,
command setup/hold, jitter and PVT.

At 54 MHz with an 8 ns injected delay, the corrected full-ROM model fails
beat zero at 225 degrees but passes at 135 degrees, including exact upload,
sentinel and guest output. This demonstrates the expected read-window tradeoff;
it does not check output command/write setup.

Before correcting burst capture, the IM pipeline at 54 MHz passed the high-address
1 MiB/all-bank/end-of-RAM program and instruction-coherence benchmark. The
repeated 512-byte-array benchmark takes **362,612 cycles / 6.715 ms**, versus
**2,389,660 cycles / 44.253 ms** for the earlier serial cached image at the same
frequency: about **6.59x** on this workload. It is not a general FP-RISC speedup
measurement. Board checks also passed 11,520 RV32I, 4,608 RV32M and 3,852 bus
comparisons, plus the counter/trap checks.

Before correcting burst capture, the burst controller passed the physical full-capacity
48 MHz test: all 8 MiB, **12,582,912 comparisons**, including poisoned byte masks
and retention. Tested image SHA-256:
`cda64be4ba9b47ee430b3324818ceaa16aed98c0b06d14763388fdb46b16da8b`.

## Reproduction

From the repository root, generate either CPU without running the licensed
vendor flow:

```sh
cabal run -v0 clash -- -isrc -hide-package haskplayground src/SdramPipeline.hs \
  --verilog -fclash-clear -outputdir output/tangnano20k/sdram-generated/SdramPipeline-0
cabal run -v0 clash -- -isrc -hide-package haskplayground -DRISCV_COMPRESSED \
  src/SdramPipeline.hs --verilog -fclash-clear \
  -outputdir output/tangnano20k/sdram-generated/SdramPipeline-1
python3 boards/tangnano20k/sdram/check_pipeline_rtl.py
python3 boards/tangnano20k/sdram/check_pipeline_rtl.py --compressed \
  --generated output/tangnano20k/sdram-generated/SdramPipeline-1/SdramPipeline.topEntity
python3 boards/tangnano20k/sdram/check_pipeline_rtl.py --compressed --boot-loader --pin-model \
  --generated output/tangnano20k/sdram-generated/SdramPipeline-1/SdramPipeline.topEntity
python3 boards/tangnano20k/sdram/check_pipeline_rtl.py --compressed --boot-loader --pin-model \
  --uart-bit-cycles 32 --pin-freq-mhz 27 --pin-phase-degrees 225 --pin-tac-ns 6 \
  --generated output/tangnano20k/sdram-generated/SdramPipeline-1/SdramPipeline.topEntity
python3 boards/tangnano20k/sdram/check_burst.py --freq-mhz 48
iverilog -g2012 -s pipeline_cache_tb -o /tmp/pipeline-cache-tb \
  boards/tangnano20k/sdram/pipeline_cache.v boards/tangnano20k/sdram/pipeline_cache_tb.v
vvp /tmp/pipeline-cache-tb
```

The full UART loader simulation can take several minutes. The runner uses
Verilog 2005 for generated Clash identifiers that collide with SystemVerilog
keywords. `--uart-bit-cycles 32` changes only UART reload constants in ignored
simulation copies for faster debugging; it is not a hardware timing test.
The pin model defaults to 48 MHz, a 180-degree clock and zero output-access
delay. Timing overrides are simulation inputs, not SDRAM data-sheet limits.

Build separate vendor images with explicit output paths:

```sh
SDRAM_FREQ_MHZ=27 SDRAM_RVC=1 SDRAM_OUT="$PWD/output/tangnano20k/sdram-pipeline-c27" \
  boards/tangnano20k/sdram/build.sh pipeline
# Faster clocks below are experiments pending the physical checks described above.
SDRAM_FREQ_MHZ=48 SDRAM_RVC=1 SDRAM_OUT="$PWD/output/tangnano20k/sdram-pipeline-c48" \
  boards/tangnano20k/sdram/build.sh pipeline
SDRAM_FREQ_MHZ=48 SDRAM_OUT="$PWD/output/tangnano20k/sdram-burst48" \
  boards/tangnano20k/sdram/build.sh burst-test
```

`core` aliases `pipeline`; `serial` selects the earlier word cache and supports
`SDRAM_CACHE=0`. The pipelined image requires its fixed-latency cache. The flow
rejects internal timing violations. For board replay, load the intended SRAM
image and pass the matching clock to every host check:

```sh
openFPGALoader -b tangnano20k output/tangnano20k/sdram-pipeline-c27/impl/pnr/sdram_test.fs
python3 boards/tangnano20k/sdram/check_core.py --freq-mhz 27
python3 boards/tangnano20k/sdram/check_cache.py --freq-mhz 27
python3 boards/tangnano20k/check_counters.py --freq-mhz 27 --sdram
```

The ROM retains the 64 KiB upload limit; data, heap and stack may use all 8 MiB.
`M` clears only the first 64 KiB. Ctrl-C resets the CPU while accepted writes
drain in order; the hardware reset button also resets the cache/write queue and
can discard queued writes. Ordinary `FENCE` does not yet drain the posted-write
queue for an external memory observer. DMA/second-master coherence requires an
explicit drain/fence protocol before integrating such a master. `FENCE.I` and
single-core instruction/data coherence are covered above.
